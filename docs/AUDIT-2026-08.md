# Аудит crm-import-converter — готовность к деплою на ms1

Дата: 2026-08-17 · Ревизия: `61b180c` · Тестовый файл: `Ernesto crm.xlsx` (436 строк)
Цель: микросервис на Hetzner ms1 (Debian 13 / py3.13) за nginx, рядом с другими сервисами.

---

## Вердикт: 5/10 — не деплоить как есть

Аудит делали независимо два агента: Claude (этот отчёт) и Codex (gpt-5.6-sol, reasoning
`max`, раздел «Второй аудит» ниже). Оценки разошлись — 6/10 против 3/10 — потому что Codex
нашёл то, что я пропустил: **дефолтные настройки молча портят данные**. Я перепроверил все
его находки собственными тестами, все подтвердились. Итоговая оценка — 5/10.

Код хорошего качества и, что редкость, **честный**: `docs/DEVELOPER.md` §9 сам перечисляет
почти всё, что не сделано инфраструктурно (нет аутентификации, нет CSRF, нет rate limiting,
один воркер). Бизнес-логика работает и воспроизводит заявленные в README числа. 40/40
тестов проходят. Формат вывода совпадает с тем, что требует Битрикс24.

Три причины не деплоить как есть:

1. **Лимиты, которые сервис сам себе объявил, на общей машине означают OOM.** Файл 19.8 МБ,
   проходящий все проверки (`MAX_ROWS`, `MAX_COLS`, 25 МБ), удерживает **3.4 ГБ** и
   парсится **274 секунды**. `MAX_SESSIONS=50` разрешает 50 таких по 6 часов. На ms1 OOM
   killer выберет жертву по размеру — это может быть сосед, а не виновник.
2. **Дефолты портят данные молча** (найдено Codex, перепроверено): комментарии режутся по
   запятым при мердже, CP1252-файл декодируется как CP1251 без ошибки, отчёты для Excel не
   экранируются никогда. См. «Второй аудит».
3. **Нет аутентификации**, а внутри персональные данные клиентов.

Реалистичный объём работ: **2–3 дня** (было бы «день», если бы не пункт 2).

## Соответствие формату Битрикс24 — совпадает

Битрикс24 CRM принимает импорт **только в CSV** (xlsx не поддерживается — менеджеру
пришлось бы сохранять вручную, что и делает этот сервис). Разделитель полей на выбор:
таб / точка с запятой / запятая. Кодировка выбирается в мастере, рекомендуется UTF-8.
Несколько значений в одно поле (несколько телефонов) — **через запятую**.

Фактический вывод сервиса:

```
BOM: да (utf-8-sig)   CRLF: да   разделитель: ;   14 колонок
Company Name;Lead Name;Mobile Phone;Home Phone;Other Phone Number;Corporate Website;
Other Website;Work E-mail;Home E-mail;Other E-mail;Country OUTREACH;Outreach comment;Comment;Source

Mobile Phone = '+52 3312395218, +52 33 2234 6879'
Work E-mail  = 'gcalderon.globaltherapy@gmail.com, gerasan_25@hotmail.com'

ячеек, содержащих ";" (сломали бы разделитель): 0
```

Вывод: `;` + запятая для мультизначений — **ровно то, что документирует Битрикс**.
Имена колонок совпадают с английскими подписями полей лида в Битриксе
(Mobile Phone / Home Phone / Other Phone Number, Work/Home/Other E-mail, Corporate/Other
Website), так что автосопоставление в мастере должно сработать. `Country OUTREACH` и
`Outreach comment` — пользовательские поля, их надо заранее создать в портале.

Два места, которые надо проверить на живом портале до передачи менеджерам:

1. **`Source = 'import'`.** В Битриксе источник лида — справочник (`crm.status.list`,
   `ENTITY_ID=SOURCE`), а не свободный текст; штатные значения вида `CALL`, `WEB`.
   Если в портале нет источника с названием «import», поле просто не подтянется.
   Либо создать такой источник, либо вывести `source_value` в UI (в опциях он уже есть,
   `converter.py:934`, но на форму не выведен).
2. **BOM.** По умолчанию `utf-8-sig`. Мастер импорта может прочитать первый заголовок как
   `﻿Company Name` и не сопоставить колонку. В приложении уже есть опция
   «UTF-8 without BOM» — прогнать оба варианта один раз и поставить дефолтом тот,
   что сработал.

## БЛОКЕРЫ (обязательно до деплоя)

### 1. Заявленные лимиты = OOM на общей машине

`converter.py:630-631` — `MAX_ROWS = 200_000`, `MAX_COLS = 300`; `app.py:32` — 25 МБ.
Измерено (отдельный процесс на кейс, `tracemalloc` + RSS):

| Файл (всё под лимитами) | На диске | Парсинг | Удержано в RAM | Peak RSS |
|---|---|---|---|---|
| 436 × 5 (реальный) | 0.01 МБ | 0.1 с | 1 МБ | 33 МБ |
| 50 000 × 10 | 1.44 МБ | 17 с | 221 МБ | 565 МБ |
| 150 000 × 20 | 7.6 МБ | 99 с | 1 330 МБ | 3 233 МБ |
| **199 000 × 40** | **19.8 МБ** | **274 с** | **3 376 МБ** | **5 543 МБ** |

Последняя строка проходит все проверки сервиса. И это только 40 колонок из
разрешённых 300. Плюс подтверждено на живом сервисе: **8 сессий скромных файлов →
1.02 ГБ RSS** у процесса waitress, и память не отдаётся, потому что `SESSIONS` держит
все строки 6 часов (`app.py:56`, `SESSION_TTL_SECONDS`).

Причина, почему проверка не спасает: `read_xlsx` (`converter.py:635-639`) вызывает
`load_workbook(path, data_only=True)`, который строит полную объектную модель, и только
**после этого** сравнивает `ws.max_row` с `MAX_ROWS`. Гард срабатывает, когда память уже
израсходована — на файле в 400k строк (2 МБ на диске) он честно кинул
`TableTooLargeError`, но уже съев 153 МБ.

Починка — см. отдельный раздел **«Откуда нагрузка и как её убрать»** ниже: там замеры,
из которых видно, что интуитивный фикс (`read_only=True`) экономит память, но **не даёт
ускорения вообще**, а реальный выигрыш даёт замена ридера (10x) и один fast path в
`build_records` (2.1x).

И независимо от кода — **жёсткая крышка в systemd**, чтобы этот сервис не мог утащить
соседей:
```ini
MemoryMax=1200M
MemoryHigh=900M
```
Плюс снизить лимиты до реальности задачи (списки менеджеров — сотни строк, не сотни
тысяч): `MAX_ROWS=20_000`, `MAX_CONTENT_LENGTH=8*1024*1024`, `MAX_SESSIONS=10`.

### 2. Сервис не отвечает во время обработки

Замер на живом сервисе, `waitress --threads=4`, 4 параллельные загрузки файла **1.44 МБ**
(маленького по меркам лимитов):

```
4 параллельные загрузки: суммарно 30 с, каждая 18-19 с
/healthz во время работы: max 16 003 мс, медиана 2 мс
```

`/healthz` завис на **16 секунд**. Работа CPU-bound и под GIL, поэтому потоки waitress не
помогают: 4 занятых потока — и пятый запрос стоит в очереди. Health-check systemd/nginx
будет флапать при каждой реальной загрузке, а один файл на 20 МБ заблокирует поток на
274 секунды.

Починка (без переписывания на очередь):
* `--threads=2`, чтобы один клиент не мог занять весь пул;
* в nginx `proxy_read_timeout 300s` для `/api/`, иначе 504 на середине обработки;
* health-check дёргать по `/healthz` с большим таймаутом и не считать флап падением;
* лимиты из блокера №1 сокращают худший случай с 274 с до единиц секунд — это и есть
  главное лекарство.

### 3. Пять необработанных HTTP 500 на `/api/convert` от мусорного JSON

Проверено запросами к живому сервису с валидным `session_id`:

| Тело запроса | Ответ |
|---|---|
| `mapping: {"abc": "company_lead"}` | **500** |
| `mapping: {"1:2:3": "mobile_phone"}` | **500** |
| `mapping: {"2:x": "mobile_phone"}` | **500** |
| `mapping: ["a","b"]` (список вместо объекта) | **500** |
| `options: ["x"]` (список вместо объекта) | **500** |
| `options: {"source_value": {"a":1}}` | **500** |
| `mapping: {"-1": "company_lead"}` | 200, **молча берёт последнюю колонку** |

Причины: `int(key)` на клиентских ключах (`converter.py:1026` в сортировке и
`converter.py:964-984` в `_atoms_for_key`), `mapping.values()` без проверки типа
(`app.py:238`), `(opts or {}).items()` в `normalize_options` (`converter.py:948`),
`value.encode()` над не-строкой в `fit_to_encoding` (`converter.py:1201`).

Для публичного эндпоинта это «уронить запрос по желанию» + мусорные трейсбеки в journald.
Починка — один блок валидации в `app.py:convert` перед вызовом конвертера:

```python
KEY_RE = re.compile(r'^\d{1,3}(:\d)?$')
if not isinstance(mapping, dict) or not isinstance(options, dict):
    return jsonify({'error': 'mapping and options must be objects.'}), 400
if any(not KEY_RE.match(str(k)) for k in mapping):
    return jsonify({'error': 'Invalid column key in mapping.'}), 400
```
и `o['source_value'] = str(o['source_value'] or SOURCE_VALUE)[:100]` в
`normalize_options`. `KEY_RE` заодно закрывает `-1` и абсурдные индексы.

Отдельно — глобальный обработчик, чтобы любая будущая ошибка не отдавала HTML-500:
```python
@app.errorhandler(Exception)
def unhandled(e):
    app.logger.exception('unhandled')
    return jsonify({'error': 'Internal error.'}), 500
```

### 4. `debug=True` + `host='0.0.0.0'` в точке входа

`app.py:366`: `app.run(host='0.0.0.0', port=PORT, debug=True)`.

README сам показывает `py app.py` как способ запуска. Если это когда-нибудь выполнится на
ms1 — Werkzeug debugger отдаёт `/console`, то есть исполнение произвольного кода на
сервере, и слушает на всех интерфейсах. `docs/DEVELOPER.md:379` предупреждает словами,
но код не мешает.

```python
if __name__ == '__main__':
    app.run(host=os.environ.get('HOST', '127.0.0.1'), port=PORT,
            debug=os.environ.get('FLASK_DEBUG') == '1')
```

### 5. Каталог загрузок жёстко зашит внутрь кода

`app.py:27-29`:
```python
BASE_DIR = os.path.dirname(os.path.abspath(__file__))
UPLOAD_DIR = os.path.join(BASE_DIR, 'uploads')
os.makedirs(UPLOAD_DIR, exist_ok=True)
```
Env-override нет. На ms1 код обычно root-owned, сервис — под своим юзером: либо падение
при импорте, либо (если каталог доступен на запись) таблицы с персональными данными
лидов лежат внутри git-каталога. `os.makedirs` на импорте вдобавок делает модуль
непригодным для импорта в тестах на read-only ФС.

```python
UPLOAD_DIR = os.environ.get('UPLOAD_DIR', os.path.join(BASE_DIR, 'uploads'))
```
и деплой с `UPLOAD_DIR=/var/lib/crm-import/uploads`.

### 6. Нет аутентификации, а внутри — персональные данные

`docs/DEVELOPER.md:396-403` объявляет это осознанным решением для инструмента внутренней
сети. Но задача — публичный микросервис на ms1. Загружаются списки клиентов (имена,
телефоны, email), результаты 6 часов доступны по URL без всякой проверки. Плюс
`multipart/form-data` — CORS-simple, поэтому чужая страница может cross-origin
отправить POST на `/api/upload` браузером менеджера и жечь CPU сервера (ответ она не
прочитает, но нагрузку создаст).

Не код — конфиг: basic auth в nginx на весь location, либо allowlist по IP офиса.
Обязательно, раз это персональные данные.

## ВАЖНОЕ (починить скоро, но не блокирует)

7. **Двойной `charset` в `Content-Type`** — `app.py:355`. Реальные ответы:
   ```
   utf-8-sig -> text/csv; charset=utf-8; charset=utf-8
   cp1251    -> text/csv; charset=cp1251; charset=utf-8     <-- противоречие
   ```
   `send_file(mimetype='text/csv; charset=X')` — Werkzeug добавляет свой charset поверх.
   Клиент, берущий последний параметр, прочитает cp1251-байты как UTF-8 → мохито из
   символов. Починка: `mimetype='text/csv'`, затем
   `resp.headers['Content-Type'] = f'text/csv; charset={charset}'`.

8. **Телефоны: 13 из 362 (4%) в выводе недозвонные.** `normalize_phone`
   (`converter.py:288`) приписывает `+` любому номеру от 8 цифр, включая внутренние:
   ```
   '098 554 7600'  -> '+098 554 7600'   ни один код страны не начинается с 0
   '6269-5539'     -> '+6269-5539'      8 цифр, кода страны нет вовсе
   '449 478 2400'  -> '+449 478 2400'   мексиканский местный, должно быть +52 449...
   ```
   Плюс неизвестное число «правдоподобных, но неверных»: `+449...` выглядит как валидный
   номер (код 44 — Великобритания) и молча уедет в Битрикс мёртвым лидом. На тестовом
   файле таких «угаданных» 108 из 436.
   Сервис об этом предупреждает в UI и даёт `default_country_code` — то есть лечится
   процессом: **менеджер обязан указывать код страны**. Стоит (а) убрать ведущий `0`
   перед подстановкой кода, (б) не ставить `+`, если кода страны нет и `default_cc` пуст —
   помечать `invalid` и выносить в отчёт, а не молча портить.

9. **`requirements.txt` не запинен** — `Flask>=3.0`, `openpyxl>=3.1`, `waitress>=3.0`.
   Пересборка через полгода поставит другие версии. Запинить точно (`==`) и хранить
   рядом сгенерированный lock.

10. **Один воркер — требование, ничем не защищённое.** `SESSIONS` в памяти процесса
    (`app.py:56`). `gunicorn -w 4` даст случайные «Session not found or expired», и
    диагностировать это будет мучительно. Либо ассерт на старте, либо перенести сессии
    в Redis/файлы. Минимум — комментарий в самом unit-файле.

11. **`cleanup_sessions()` вызывается только из `/api/upload`** (`app.py:122`). Если
    неделю никто не загружает файлы, персональные данные и `uploads/` лежат сверх
    заявленных 6 часов. systemd timer с `find -mtime` или вызов из `/healthz`.

12. **Утечка внутренних ошибок клиенту** — `app.py:147`:
    `f'Could not read the file: {e}'`. Текст исключения openpyxl может содержать
    серверные пути. Логировать полностью, клиенту отдавать общее.

13. **Формула-инъекция.** В выводе на тестовом файле **308 ячеек начинаются с `+`/`=`**
    (почти все — телефоны). `sanitize_formulas=False` по умолчанию — для Битрикса это
    правильно, ведущий `'` испортил бы номер. Но README предполагает, что менеджер
    откроет файл в Excel: враждебная исходная таблица с `=HYPERLINK(...)`/`=cmd|...`
    пройдёт насквозь. Раз файлы приходят от внешних людей — либо описать это в
    инструкции, либо сделать `sanitize_formulas` дефолтом для «файла на посмотреть»
    и выключать только для импорта.

## МЕЛОЧИ

14. `MAX_SESSIONS` off-by-one: `cleanup_sessions()` бежит **до** добавления новой сессии
    (`app.py:122` → `app.py:160`), фактический потолок 51.
15. `_drop_session` делает `shutil.rmtree` под `SESSIONS_LOCK` (`app.py:64-66`) —
    блокирующий I/O под локом, держит все остальные запросы.
16. Fallback в `read_table` (`converter.py:701-709`) — мёртвый код: `ALLOWED_EXT`
    разрешает только 4 расширения, и все четыре обработаны ветками выше. Побочный
    эффект: CSV, переименованный менеджером в `.xlsx`, отвергается с невнятным
    `File is not a zip file` (проверено). Либо разрешить fallback по содержимому,
    либо дать понятный текст ошибки.
17. Нет ни `Dockerfile`, ни systemd unit, ни примера nginx location — деплой полностью
    руками, воспроизводимость нулевая.
18. `reference_import.csv` — эталон, на который ссылаются README, `converter.py:89`,
    `SUPPORT.md`, `DATA-ANALYSIS.md` — **в репозитории отсутствует**. Проверить
    соответствие формату нечем.
19. Нет настройки логирования: ни формата, ни уровня. Всё уходит в stderr → journald.
    Для одного сервиса приемлемо, но access-логов запросов нет вообще.

## План деплоя на ms1

Порядок: сначала правки 3, 4, 5 (полчаса), потом обвязка, потом блокер 1 (стриминг).
Блокеры 2 и 6 закрываются конфигом.

**1. Правки в коде** (блокеры 3, 4, 5 + важное 7, 9):
валидация `mapping`/`options`, `debug` из env, `UPLOAD_DIR` из env, `Content-Type`,
запинить requirements, снизить `MAX_ROWS`/`MAX_CONTENT_LENGTH`/`MAX_SESSIONS`.

**2. Раскладка на сервере**
```bash
useradd -r -s /usr/sbin/nologin crmimport
install -d -o crmimport -g crmimport /var/lib/crm-import/uploads
git clone <repo> /opt/crm-import && cd /opt/crm-import
python3.13 -m venv venv && venv/bin/pip install -r requirements.txt
```

**3. systemd** — `/etc/systemd/system/crm-import.service`
```ini
[Unit]
Description=CRM import converter
After=network.target

[Service]
User=crmimport
WorkingDirectory=/opt/crm-import
Environment=UPLOAD_DIR=/var/lib/crm-import/uploads
Environment=SESSION_TTL_SECONDS=7200
Environment=MAX_SESSIONS=10
# ВАЖНО: ровно один воркер — состояние сессий живёт в памяти процесса
ExecStart=/opt/crm-import/venv/bin/waitress-serve \
    --host=127.0.0.1 --port=5101 --threads=2 app:app
Restart=always
MemoryHigh=900M
MemoryMax=1200M
# песочница: сервис парсит файлы из интернета
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/lib/crm-import
[Install]
```

## Второй аудит (Codex, gpt-5.6-sol, reasoning max) — что он нашёл сверх моего

Codex поднял свою копию сервиса в `/tmp`, прогнал файл, дополнительно запустил
`gunicorn -w 2` и `pip-audit`. Пересечение с моим аудитом большое (он независимо
подтвердил: memory-DoS через сжатый XLSX 70 КБ → 67 МБ XML, отсутствие авторизации,
500 на невалидном mapping, `debug=True`, hardcoded `UPLOAD_DIR`, двойной `charset`,
незапиненные requirements, придуманные международные номера — 108 штук, те же, что и у меня).

Полный текст его отчёта: `codex-audit.md` рядом с этим файлом.

**Ниже — только то, чего у меня не было. Каждый пункт я перепроверил своим тестом.**

### 1. Мердж режет свободный текст по запятым — ПОДТВЕРЖДЕНО

`_merge_group` (`converter.py:1372-1384`) применяет `_split_multi` (разбиение по запятой)
ко **всем** полям, включая Comment. Мой тест:

```
вход  : 'Call Monday, urgent' + 'Call Tuesday, urgent'
выход : 'Call Monday, urgent, Call Tuesday'
```

Слово `urgent` из второго комментария исчезло — оно совпало с `urgent` из первого и было
отброшено как «дубликат». Для телефонов/email это правильное поведение, для свободного
текста — потеря данных. `_split_multi` должен применяться только к phone/email/URL.

### 2. Отчёты никогда не экранируются от формул — ПОДТВЕРЖДЕНО

Даже при `sanitize_formulas=True`:

```
основной CSV      : ["'=1+1", "'=1+1"]     <- экранировано
duplicates_report : ['1', '=1+1', ...]     <- НЕ экранировано
```

`_escape_formula` вызывается только из `records_to_rows` (`converter.py:1139-1148`).
`duplicates_report_rows` и `fixes_report_rows` пишутся напрямую. При этом отчёты —
единственные файлы, которые **заведомо** открывают в Excel (`app.py:270`: «Reports are
for humans in Excel»). Здесь опциональной защиты быть не должно.

### 3. Входной CSV в CP1252 молча превращается в кашу — ПОДТВЕРЖДЕНО

`read_csv_bytes` (`converter.py:661`) перебирает `utf-8-sig, utf-8, cp1251, latin-1`.
CP1251 идёт раньше CP1252 и **никогда не падает** на однобайтовых данных:

```
байты были cp1252 : 'Clínica México;José'
приложение прочло : ['Clнnica Mйxico', 'Josй']
```

Исключения нет, предупреждения нет — испанские имена клиентов просто становятся другими.
Автоматически различить CP1251 и CP1252 нельзя; нужен явный выбор входной кодировки в UI
(выходная там уже есть). Для xlsx проблемы нет — только для CSV.

### 4. Дедупликация по телефону склеивает разные компании — ПОДТВЕРЖДЕНО, но с нюансом

Codex предложил выключить `dedupe_by_phone` по умолчанию. Я проверил все группы,
склеенные **только** по телефону, и картина мягче, чем у него:

```
5 групп из 57 склеены исключительно по телефону:
  [125, 205] 'Esthetic Store'            + 'Esthetic Store Colombia'          <- верно
  [163, 181] 'Beauty Skin'               + 'Beauty Skin | Médicos Estéticos'  <- верно
  [172, 307] 'Academia Medicina Estética'+ 'Academia Internacional de Med...' <- верно
  [349, 437] 'CosmoPro'                  + 'Cosmo Pro México (cosmopro.mx)'   <- верно
  [294, 321] 'Supliestetica Oriental SRL'+ 'Dermclar República Dominicana'    <- ОШИБКА
```

4 из 5 — настоящие дубликаты, которые матчинг по имени не поймал; телефон их вытащил.
Один — ложное срабатывание (общий номер дистрибьютора или опечатка). Так что
выключать не надо — **это полезная функция с 20% ложных срабатываний**. Правильнее:
оставить включённой, но в UI помечать группы, склеенные только по телефону, как
«проверить вручную» — данные для этого уже есть, `groups[].matched_on` их отдаёт.

### 5. Колонки сверх лимита обрезаются молча — ПОДТВЕРЖДЕНО

305 колонок на входе → 300 на выходе, `200 OK`, ни ошибки, ни warning
(`converter.py:637` и `683`). Менеджер не узнает, что 5 колонок пропали.

### 6. Прочее от Codex, что я считаю верным и важным

* **TTL не проверяется при `convert`/`download`** — только при следующем `/api/upload`.
  Просроченная сессия продолжает отдавать персональные данные, пока никто не загрузит
  новый файл. Нужна проверка `created + TTL` в каждом обращении.
* **`gunicorn -w 2` эмпирически даёт 5×404 «Session not found» из 20** — подтверждает,
  что требование «один воркер» надо защищать, а не документировать.
* **Артефакты сессии перезаписываются** при повторном `/api/convert` — тот же
  download-URL начинает отдавать другое содержимое; при параллельных запросах возможен
  недописанный файл. Нужны временный файл + `os.replace()`.
* **Читается только активный лист** — остальные игнорируются без предупреждения.
  Для файлов менеджеров (часто multi-sheet) это тихая потеря данных.
* **Транзитивные склейки union-find**: A совпала с B по имени, B с C по email → все три
  становятся одной компанией, хотя A и C не связаны ничем.
* `Cache-Control: private, no-store` на скачивания с контактами.
* `.txt` разрешён в `ALLOWED_EXT`, но не перечислен в тексте ошибки.
* Нет ни одного HTTP-теста: все 40 покрывают только `converter.py`.

### Где Codex, по-моему, перегибает

* «CSV formula injection включена по умолчанию» как блокер для **основного** CSV —
  спорно. `sanitize_formulas=False` по умолчанию сделано осознанно: ведущий `'` испортил
  бы телефоны (`+52...`), а файл идёт в Битрикс, а не в Excel. Для **отчётов** его
  претензия полностью верна. Его же вариант фикса (не экранировать значения, совпадающие
  с `^\+\d+$`) — хорошее решение, стоит взять.
* Требование `phonenumbers` вместо самописной нормализации — правильно по сути, но это
  новая зависимость и переделка UI (код страны `52` → регион `MX`). Для 436-строчных
  списков достаточно: убрать ведущий `0` и не ставить `+` без известного региона.
* `pip-audit --local` показал «No known vulnerabilities» — но это про установленный
  набор, а `requirements.txt` его не фиксирует. Вывод верный, но силы у него меньше,
  чем кажется.

## Откуда нагрузка и как её убрать

Вопрос был: откуда такая нагрузка и можно ли оптимизировать. Разобрал по частям
профилировщиком. Все замеры — файл 1.44 МБ на диске, 50 000 строк × 10 колонок.

### Куда уходит время сейчас

```
load_workbook(data_only=True)                14.9s   peak 207 MB   <-- 82% всего чтения
  пас 1: ws.cell(r,c).value                   0.3s
  пас 2: ws.cell(r,c).hyperlink               0.3s
clean_text по всем ячейкам                    1.1s
--------------------------------------------------------------
converter.read_xlsx() целиком                18.1s   peak 221 MB
```

Нагрузка — **не в бизнес-логике очистки** (1.1 с из 18), а в парсинге XML внутри openpyxl.
Файл 1.44 МБ разжимается в **42 МБ XML** (коэффициент 29x), и openpyxl создаёт Python-объект
`Cell` на каждую из 500 000 ячеек — по ~30 мкс на ячейку.

### Что НЕ помогает (проверено, вопреки ожиданию)

```
read_only=True + iter_rows(values_only=True)  17.7s   peak  55 MB
openpyxl как сейчас                           18.1s   peak 221 MB
```

`read_only=True` даёт **4x по памяти и ноль по времени.** Это важно: и я в первой версии
отчёта, и Codex рекомендовали стриминг как главный фикс производительности — по замерам
это неверно. Стриминг стоит делать, но ради памяти, не ради скорости.

### Что помогает

**1. Заменить ридер на `python-calamine` (Rust-парсер xlsx).** Вывод побайтово идентичен:

| Файл | openpyxl | calamine | Выигрыш |
|---|---|---|---|
| 50 000 × 10 (1.44 МБ) | 18.0 с / 221 МБ | **1.7 с / 54 МБ** | 10.3x / 4x |
| 150 000 × 20 (7.6 МБ) | 105.7 с / 1293 МБ | **9.7 с / 263 МБ** | 10.9x / 5x |

`identical output? headers True, rows True` — проверено на обоих файлах.

Единственная загвоздка: calamine не отдаёт гиперссылки, а они используются как fallback
для url-полей (в реальном файле их 283). Решается точно и дёшево — гиперссылки лежат в
маленьком блоке `<hyperlinks>` + `_rels`, читаются независимо от числа строк:

```
openpyxl : 283 гиперссылки  (полное чтение 0.03 с на этом файле)
из zip   : 283 гиперссылки  (целевое чтение 5 мс)
одинаковый набор target-URL: True    симметрическая разница: 0
```

~20 строк на `iterparse`. **Использовать `defusedxml.ElementTree`, не stdlib** — парсим
файлы из интернета, а stdlib-ET уязвим к entity-атакам.

**2. Fast path для text-полей в `build_records`.** После замены ридера `build_records`
становится 86% времени. Причина: для text-типизированной цели используется только
`atoms['text']`, но `_atoms_for_key` перед этим прогоняет **все** регулярки на
email/url/телефоны, и результат выбрасывается — код делает `continue` до блока autofix
(`converter.py:1043-1046`). В профиле видно **2 980 001 вызов `re.sub`** на 30 000 строк.

Так как `rows` уже прошли `clean_text` в ридере, для text-цели весь вызов сводится к
одному индексу в списке:

```
build_records как есть      2.58s
build_records с fast path   1.22s   -> 2.1x
IDENTICAL OUTPUT? records True, fixes True
```

Проверено на реальном файле при 4 наборах опций (`{}`, `autofix_types=False`,
`default_country_code='52'`, `skip_rows_without_name=True`) — везде идентично.
Реализация лежит в `opt_build_records.py` (в scratchpad, ~40 строк diff).

**3. Итог по конвейеру целиком, тот же файл:**

```
CURRENT   openpyxl + build_records       read 18.1s + rest 42.2s = 60.3s   peak 304 MB
OPTIMIZED calamine + text fast path      read  1.8s + rest 14.0s = 15.8s   peak 137 MB
identical CSV output: True (50 000 строк)   -> 3.8x быстрее, 2.2x меньше памяти
```

**4. И самое главное — снизить лимиты, потому что нагрузка самодельная.**

Реальный файл заказчика — **436 строк, обрабатывается за 0.1 с**. Вся проблема
существует только потому, что сервис объявляет `MAX_ROWS=200_000` и `MAX_COLS=300`,
которых задача не требует: менеджер конвертирует свой список клиентов, а не выгрузку
из хранилища. Три константы:

```python
MAX_ROWS = 20_000            # вместо 200_000
MAX_COLS = 60                # вместо 300
MAX_CONTENT_LENGTH = 8 << 20 # вместо 25 МБ
```

Худший допустимый случай падает с 274 с до единиц секунд **без единой строки нового кода**.

### Порядок действий

| Шаг | Эффект | Стоимость |
|---|---|---|
| 1. Снизить `MAX_ROWS`/`MAX_COLS`/`MAX_CONTENT_LENGTH` | худший случай 274 с → ~2 с | 3 константы |
| 2. Не хранить `rows` дольше нужного + убрать матрицу `None`-гиперссылок | памяти в разы меньше | мелочь |
| 3. Fast path для text-полей | 2.1x на `build_records` | ~40 строк, вывод идентичен |
| 4. `python-calamine` + гиперссылки из zip | 10x на чтении | 1 зависимость + ~20 строк |
| 5. `MemoryMax` в systemd | сервис физически не может утащить соседей | 2 строки конфига |

Шаги 1, 2 и 5 закрывают проблему для этой задачи полностью. Шаги 3 и 4 нужны только если
кто-то реально начнёт грузить десятки тысяч строк — тогда они дают ещё 3.8x.
